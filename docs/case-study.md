# 案例說明：Feedback Insight Hub

> 顧客回饋 → 可驗證的 AI 分析 → 改善追蹤的閉環系統。本頁給第一次看這個專案的人：問題是什麼、我做了哪些取捨、成果在哪裡。
> 技術細節見 [技術展示](technical-showcase.md)，AI 評估數據見 [AI 輸出評估](ai-eval.md)。

## 問題

小型店家與團隊收得到問卷回饋，卻很少真正用上：統計要另外做、開放式回答沒人讀完、看完也不知道從哪裡改。
這個系統把三件事串成一條線：

1. **收集**：登入制問卷，回覆與填答者綁定，改善完成後能回頭通知當初提出意見的顧客。
2. **分析**：依題目資料型態自動做統計檢定與中文文字分析，再由 LLM 寫成營運摘要與改善草稿。
3. **追蹤**：改善草稿可轉成改善項目，有狀態流程與顧客通知。

## 我的角色

這原本是產學課程的分組結業作品。我擔任 PM：提出構想、分工、搭起專案骨架，前端也大部分由我完成。
結業後我把它獨立成個人專案，加入 LLM 分析、版本化發布、真實資料（TripAdvisor 201,295 筆評論）與桌面工作台。

## 架構重點：網站收資料，本機算，版本化發布

```
顧客 ──填答──> 網站（Render, Django） ──排程工作──> 本機 Worker（統計／文字／Gemini）
                    ▲                                        │
                    └──────── 只讀「已發布」的有限結果 ◀──────┘  （發布前核對版本與租約）
```

- 網站不在 request 裡做任何運算；分析由本機 Worker 完成後**版本化發布**，過期的 Worker 不能覆蓋較新的結果。
- 20 萬筆評論留在本機 Parquet，雲端資料庫只放問卷定義與彙總結果（免費方案上限 500 MB）。
- 同一套 Django 程式也能以「本機節點」模式打包成 Windows EXE（系統匣＋本機主控台），CI 以雲端與本機兩種模式各跑一次全部測試。

## 核心難題：讓 LLM 寫的數字可以被信任

營運摘要裡如果出現一個編造的數字，整份報告就失去可信度。這是這個專案最主要的 AI 工程問題，解法經歷了三個階段：

| 階段 | 做法 | 優點 | 問題 |
|---|---|---|---|
| 一、禁止數字 | 文字裡出現任何阿拉伯數字就拒絕；精確數值只由網頁依引用的證據卡片顯示 | 結構上不可能編造 | 文字空泛；題目名稱本身帶數字（如「1–10 分」）也被誤擋 |
| 二、照抄＋查核（現行） | 數字必須能對應到所引用 evidence 的數值、樣本數或標籤中的數字，對不上就擋下 | 文字具體可讀 | 依賴查核規則；正式重跑時連續被擋 |
| 三、引用代號（實驗中） | 模型寫 `{E012}`，程式依 evidence 填入實際數值，並自動把來源補進引用清單 | 來源明確，可自動補引用 | 引用清單有上限；模型不會 100% 只寫代號 |

**從正式事故到可量化的改進**：改用新模型重跑時，綜合解析連續兩次被自己的查核擋下。處理方式：

1. **先讓錯誤可診斷**：驗證失敗時記錄被擋下的數字（只存數字、不存文字），不必多花一次付費呼叫就查出原因。
2. **分清是模型的錯還是規則的錯**：一次是模型自訂目標值（「提升至 4.5 分」）；另一次是查核程式的錯誤——
   evidence 是 −0.6235，模型寫「負相關（0.6235）」卻被誤擋。前者補強 prompt，後者修正查核規則。
3. **讓失敗局部化**：單一不合格的改善草稿只捨棄該項，不再讓整份報告失敗（與其他兩個階段一致）。
4. **建立評估工具**：用固定的測試案例與正式的驗證函式，比較不同寫法的合格率；原始輸出保存在本機，規則調整後可免費重新評分。

評估結果（[完整數據](ai-eval.md)）顯示：**主要失敗模式不是編造，而是「數字取自沒有列入引用的 evidence」**。
引用代號因為來源明確，可以自動補引用；在飲料店問卷上被擋的數字由 7 降到 3。剩下的失敗全部來自「引用數超過上限」，
下一步要用 prompt 規則解決。

## 其他工程實踐

- **工作佇列**：租約、心跳、有限重試、取消；PostgreSQL 併發測試驗證兩個 Worker 不會同時領到同一份工作。
- **資料可追溯**：外部資料記錄來源版本、內容雜湊與清理口徑；同鍵不同內容列為衝突，不覆寫。
- **統計誠實**：每項結果報告有效 N、缺失與排除原因；順序尺度不當連續變數處理；未知情緒不當成中立。
- **AI 輸出版本化**：prompt、schema 與上限的內容雜湊構成階段版本，修改 prompt 不會誤用舊結果。
- **設計先於實作**：較大的功能先寫規格、經過多輪審查再寫實作計畫（[設計文件](superpowers/specs/)）。
