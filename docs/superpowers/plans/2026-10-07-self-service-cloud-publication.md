# 自助雲端發布與後續修改流程

狀態：2026-10-07 **擱置，非本輪實作範圍**。以下歷史發布設計保留為未來提案，尚未批准、實作或驗收。
本文件不授權正式資料寫入、收件切換、部署、Gemini 或資料清理。

## 本輪收斂決定

- 已確認的歷史副本維持「僅本機」：可分析及保存，不參與雲端上傳，不計為同步失敗，也不提供無法完成的發布修復入口。
- 判定依已完成、對帳成功且 `copy_only` 的歷史匯入紀錄，不靠標題猜測；已有雲端 revision 或明確外部來源者仍核對正常上傳狀態。
- 真正的來源未登錄、分析失敗或上傳錯誤仍須提示，不能用「僅本機」掩蓋。
- TripAdvisor 沿用既有資料集登錄／發布／C3；飲料店新節點示範依原規格走限定自測收件匣，不新增第三種歷史來源契約。
- 等有實際需要保留並發布的歷史回覆，再另行審查以下提案；不是目前完成原規格的前置條件。

以下「應提供」及操作步驟均為擱置提案，不代表產品現有能力。

## 1. 目標與現況

使用者在產品介面確認一次範圍後，程式完成來源登錄、版本核對、必要分析、發布與上傳。
之後修改資料或分析設定，只需正常操作產品，無須再次請代理串接。

已核對的實作：

- `node/history.py`／`feedback/history_transfer.py` 只建立獨立本機歷史副本；不建立雲端 revision 或同步狀態。
- `cloudsync/scope.py` 因而不將歷史副本納入上傳。這道保護不能用補資料列的方式繞過。
- `cloudsync/survey_write.py` 已有一般問卷建立／修改 API；`cloudsync/datasets.py` 已有外部來源登錄。
- `feedback/analysis_jobs.py` 的發布交易呼叫 `record_publication`；已綁定來源會自動建立 C3 上傳紀錄。
- `desktop_app/node_launcher.py` 每 300 秒執行同步。不是每次分析都要手動按「立即同步」。
- 提案建立時，工作頁一般歷史副本的修復入口只返回雲端連線，形成死路；本輪已改為「僅本機」並移除該入口，不實作歷史發布。

## 2. 不混為一談的三種操作

| 使用者目的 | 程式應提供的操作 | 不可順便執行 |
| --- | --- | --- |
| 歷史副本只供本機查看 | 明確選擇「僅保存在本機」 | 自動建立雲端問卷或上傳 |
| 把既有歷史資料的分析放到網站 | 「發布歷史分析」：建立獨立結果展示目標並綁定歷史來源 | 覆蓋舊問卷、假造收據、開啟新填答 |
| 今後透過網站接收新回覆 | 另一個「啟用線上收件」流程 | 默認已獲正式切換或明文收件授權 |

外部 Parquet 來源仍走既有資料集登錄，不轉成歷史回答，也不新增另一套分析引擎。

### 必須先補的規格差異

[節點唯一分析規格](../specs/2026-10-04-node-only-analysis-design.md) 第 4 節原定飲料店流程是
「建立新節點問卷 → 100 筆模擬資料進收件匣 → 收件／分析／上傳」，**不是歷史副本結果發布**。
[雲端同步規格](../specs/2026-10-01-cloud-sync-design.md) 也沒有歷史來源的結果綁定契約。

因此「發布歷史分析」是待審查的規格增補，不能僅改 `is_cloud_synced`，不能假造 revision 或水位，
也不能把原定自測 seed 當成使用者現有資料。先完成第 4 節合約設計與審查，再實作此路徑。
本計畫不表示該增補已批准，亦不宣稱既有雲端 API 不經部署即可支援。

## 3. 使用者看到的流程

入口放在「分析工作 → 來源卡片 → 發布設定」，雲端連線警告也直接連到同一來源的設定頁。

1. **選擇用途**：僅本機、發布歷史分析、既有外部資料登錄。線上收件另外進入其受限流程。
2. **預覽影響**：來源、有效與排除筆數、資料截至時間、定義版本、目前雲端連線、將建立的新目標。
   明列「舊問卷保留、不上傳答案正文、不開啟填答、不寄信、不呼叫 Gemini」。
3. **確認一次**：OWNER 確認「建立獨立雲端展示並啟用後續自動上傳」；可返回而不變更任何資料。
4. **程式執行**：持久保存操作意圖，依序登錄、綁定、排程必要重算；網頁只顯示狀態，不執行分析。
5. **追蹤狀態**：來源綁定 → 統計／文字 → 本機發布 → 雲端收妥；只有收到套用確認才顯示完成。
6. **後續修改**：沿用正常問卷／資料集／設定入口，程式核對版本並排程；發布後自動入列與同步。

設定頁保留來源 UUID、目標 UUID、使用的定義與資料版本、最近成功發布與上傳時間，以及各階段錯誤。
「正在重算」「排隊上傳」「離線待傳」「版本衝突」不能統稱成功。
百分比只用可靠階段回報，不估算不存在的剩餘時間。

## 4. 歷史來源結果合約：實作前置門檻

必須先定義並驗證以下事項，不直接套用一般收件匣假設：

- **獨立目標**：雲端新目標 UUID 與舊線上問卷分離，保存歷史副本 → 新目標的明確對應；不改舊所有權。
- **分析正本**：仍使用本機一般 `FeedbackSubmission`／`Answer` 與既有分析服務，不複製另一套分析核心。
  新目標不得導致本機出現兩套可以各自修改、卻宣稱同一份正本的答案。
- **來源聲明**：保存可追溯的歷史匯入版本、資料包／資料指紋、問卷語意與題目對應、來源筆數。
  使用既有匯入批次／來源資訊；不要把「有匯入批次」當成 Parquet，或新增同義的資料集版本核心。
- **來源不可默換**：歷史資料或語意變更建立新的可追溯版本；舊 Worker／上傳不得把新舊來源混用。
- **數量分開**：網站分別報「歷史資料納入 N 筆」與「新收件／已同步 N 筆」。歷史資料不是收件匣資料，
  不建立虛構收據、ACK 或 `response_sequence`，不能靠一般水位 0 就宣稱歷史來源完整且最新。
- **雲端新鮮度**：雲端核對已登錄歷史來源、分析所依據的定義版本和資料指紋；不只比較發布序號。
  雲端只能驗證登錄聲明與結果一致，不能宣稱驗證了未上傳的全部答案正文。
- **隱私**：只傳問卷定義、經檢查的來源中繼資料與既有有限展示結果；原始評論、姓名、Email、帳號、
  本機路徑、ZIP 內容均不得藉此上傳。原始填答版本未知仍標未知，結果附歷史語意限制。
- **收件生命週期**：此路徑只展示結果，預設不接受新填答。由伺服器端規則保證，不能只隱藏按鈕。
  頁面與一般問卷管理的草稿／發布概念如何銜接，須在規格增補寫清楚，不能隨意偽造已發布欄位。
- **兼容／版本**：明列 API 契約版本與舊雲端不支援時的回應；若需模型變更，才增加有回退說明的 migration。
  雲端不支援時停在「需要更新雲端版本」，不得降級成不安全寫入。

## 5. 執行與重試的實作要求

### A. 意圖與確認

- OWNER、POST、CSRF、伺服器端來源範圍檢查；簽章確認有效 15 分鐘。
- 確認綁定操作者、來源／目標 UUID、來源指紋、定義版本、連線 generation 與節點身分。
- 執行前重查；預覽後資料、節點、題目或連線改變，要求重新預覽。
- 確認後持久化固定操作 ID 與目標 UUID；重複點擊、崩潰重啟沿用同一操作，不多建問卷。
- 如需新增管理流程狀態，僅承擔操作協調／對應，不取代 Survey、匯入來源、AnalysisJob、Snapshot 或 C3。

### B. 雲端登錄與本機採用

- HTTP 不放在長 DB 交易中。雲端 exact retry 必須核對相同節點、操作內容和固定目標，不能只看 UUID 存在。
- 雲端成功但回應遺失：同一身分查核／重送恢復；雲端成功、本機採用失敗時顯示可恢復狀態。
- 本機透過共同定義服務採用回覆，在短交易核對連線 generation、來源／題目與版本，並保存合法綁定。
- 不強行降低本機版本號或改寫歷史答案的 `definition_version`；兩端版本空間與新目標的對應須有明確合約。
- 若背景定義同步先到，本機仍能續接同一操作；不因來源尚未採用就丟棄已確認意圖或另造目標。

### C. 分析、發布與上傳

- 改用新的雲端定義／來源身分時，排程既有 deterministic Worker 重算；舊結果仍可查看，但不重標為新版本。
- 同一輸入版本與設定已有等待／執行中工作時不重複排程。完整分析輸入按既有固定快照契約擷取。
- 發布交易核對來源、版本、管線及 lease，並建立既有 C3 紀錄；背景同步自動送出。
- Gemini 不包含在初次接線或重試內；付費確認沿用現有入口，舊 AI 不改標成新版本。
- 只有網路／暫時性失敗自動退避重試；401 停止並要求重新連結，409 或內容衝突留待處理。
- 上傳回應遺失重送同一 UUID／序號／雜湊；收到 `stale` 顯示「保留歷史，未成為網站目前版本」。
- 單一來源失敗不得卡住其他已綁定來源；不可用一般重試重新執行已成功的建立／分析階段。

## 6. 警告與入口修正

- `cloudsync/publication_status.py` 將來源用途與錯誤分開：
  - 明確僅本機：資訊提示，不列為「同步失敗」。
  - 已要求雲端發布但未完成：可直接進入該來源的恢復頁，列入待處理。
  - 真正待傳／失敗：沿用當次發布的 C3 狀態。
- 雲端連線頁區分「沒有雲端發布意圖」與「已啟用但未完成」，不能只用沒有 revision 判斷整體失敗。
- 未選擇用途的舊副本顯示「選擇發布方式」，不替使用者默認上傳或默認已同意僅本機。
- 分析工作頁顯示歷史副本與目標的關聯，避免兩張同名卡片讓人以為有兩套獨立正本。
- 對應修改入口：`node/views.py`／`node/history.py`／`node/urls.py`、`templates/node/`、
  `cloudsync/publication_status.py`／`views.py`／`runner.py`；歷史合約會牽動 cloud API、C3 與展示讀取。
  不只在模板加一個無法完成操作的連結。

## 7. 驗收順序與交付門檻

1. **合約審查**：補入規格正本，確認歷史正本／新目標關係、數量、新鮮度、生命週期及 schema 需求。
2. **隔離單元／頁面測試**：GET 不寫 DB／不聯網；OWNER／CSRF；確認過期／操作者錯誤／來源或連線變更拒絕；
   沒有確認不建立雲端資料；僅本機不阻塞其他上傳；一般及外部來源不受影響。
3. **失敗恢復測試**：重複確認、雲端已建但回應遺失、背景同步搶先、本機提交前後崩潰、
   雲端 401／409／不支援契約、部分來源失敗、上傳 ACK 遺失、舊 Worker 晚完成。
4. **完整隔離端到端**：兩個獨立 DB 經真 HTTP，從介面確認到雲端最新結果；核對有效 N／排除／歷史與新收件數，
   舊問卷／回答／發布指標不變，原文及個資未傳出。不得以假 HTTP 單元測試取代。
5. **PostgreSQL 併發**：獨立隔離 DB 驗證同時確認、來源換版、發布競爭，僅沿用現有測試設定。
6. **封裝與 GUI**：另行授權更新 EXE；驗證重啟恢復與五分鐘背景自動上傳、登入後 Render 頁面，
   不以 smoke 或直接呼叫上傳服務宣稱正常啟動器全流程驗收。
7. **正式操作另行授權**：核對目標、備份／回復、雲端契約已部署，再由使用者在產品介面確認，
   不由代理暗中代辦串接。真實資料、雲端切換、Gemini、封存／清理各守原授權邊界。

## 8. 回退與完成定義

部署前保留舊封裝、DB、來源登錄、分析產物與操作狀態。遇故障停止該流程並保留雙方紀錄；
不自動刪除已建立的雲端目標、回退全部資料庫或反向 migration。舊網站與舊問卷繼續可用。

**完成不是代理成功跑過命令**，而是使用者能從正式介面走完一次確認；正常重啟、斷線恢復、再次修改後，
程式都能自行完成後續步驟，且雲端顯示來源、數量及版本正確。Gemini、正式收件切換及刪除不是本功能的隱含副作用。
